# 试音播放卡顿与暂停修复（053）

## 故障证据

本场试音的开场合成文件为22.08秒，流式调用从打开到消费完成用了约69秒。该调用时间包含下游发布等待，不能据此认定供应商生成本身用了69秒。播放器原来首包即播，缺包立即补零，没有启动及欠载恢复缓冲；4秒音频每21ms到达一个20ms包时，旧worklet插入约201ms静音并产生151个断点。

确认试音表达在05:04:48被选中，05:04:49发生打断及暂停，随后浏览器上报runtime-problems。旧前端先发送普通pause，再上报通用运行失败，服务端先落库为candidate_requested_pause，缺少真正的播放错误码。因此不能断言本场具体由哪个浏览器分支触发。另已复现媒体断轨先于权威取消事件到达时，正常取消被误判为致命播放失败的竞态。

三个媒体容器没有重启或OOM。05:07:21的两条LiveKit RTP EOF及候选人断线事件晚于暂停，不作为本次05:04:49暂停的已证实原因。原会话和材料保留，只读诊断；测试使用合成PCM和合成话语。

进一步只读性能诊断发现，Evidence owner每20ms领取控制命令时，会同步加载并解析组织全部历史命令。当前3353条命令的空轮询耗时p50约96.7ms，单次最长约130ms，且与音频发布共享API事件循环；这一任务开场时已经运行。现有续租调度延迟p95约249ms、max约333ms，数据库续租本身p95仅1.2ms。它是实测的事件循环阻塞来源，必须改为当前面试未完成命令的定向查询，保留租约与原子领取。

隔离真实TTS对照：105字公开测试文本快速消费得到21.6秒音频，仅用4.821秒；真实LiveKit加完整只读表达校验得到23.2秒音频，用23.656秒排空。旧/新纯PCM发送器在无命令扫描的隔离进程里都能实时发完22.08秒，因此不能把69秒全部归咎于供应商或两路发布串行。实际中文浏览器验收得到22240ms内容、22251.9ms播放跨度，欠载0次，插入静音0样本；该隔离测试不包含真实API的历史命令轮询，后续另验定向查询的性能。

组合对照已复现因果：使用同一6秒合成PCM、真实本机LiveKit和逐帧完整表达校验，同时运行20ms历史命令空轮询，旧全量读取让播放队列排空耗时12.409秒；定向索引查询后为6.016秒，两者均完整收到144000样本。旧/新轮询p50为74.085/1.557ms，事件循环调度延迟p95为98.317/7.625ms。此对照证明历史扫描会实际拖慢音频，不声称完全重现旧场次69秒中的所有负载。真实数据库仅只读复制至进程内SQLite后加索引，未修改业务资料；数字结果见 `/private/tmp/interviewer-053-combined-poll-results.json`。

## 修复边界

- 播放器先积累240ms音频，欠载后重新缓冲再续播，保持2秒容量。短尾取得final后立即排空；样本消费与设备输出时钟仍共同决定完成，缓冲静音不增加源样本数。
- 增加欠载次数/静音样本统计。进度消息限频约32ms，首声、缓冲变化和结束立即通知，减少渲染主线程负担。
- 每帧的录制音轨与浏览器PCM发布同时执行，一帧的两个操作完成后才发下一帧。共享等待预算，保留逐帧前后和等待中的所有权校验，并在每个排队发送任务实际启动时再次校验，避免排队期间撤销后仍发旧帧；任一操作失败/撤销取消另一路，最多一帧在途。
- 语音消费者与权限/期限检查同时失败时，总是回收消费者异常，避免未读取的后台Task异常。
- 每次输出分别记录供应商/解码器读取等待、媒体发布等待、已发布内容时长和50ms监控任务的最大调度延迟（`tts_provider_read_wait_ms`、`tts_transport_publish_ms`、`tts_content_duration_ms`、`tts_output_scheduler_lag_ms`）。只保留有界数值，失败/取消也计入；供应商读取时间不包含消费期间的下游背压。调度延迟是共享事件循环阻塞的线索，并非具体函数归因。
- 播放取消、暂停原因与错误诊断的最终合同及回归证据在[操作日志](change-log.md)和[接口设计](api-design.md)记录。正常取消不伪造播放完成；真实音频失败仍不允许继续未经确认的面试。

## 验收

验证必须分别检查内容完整性与播放连续性：精确样本数、设备输出结束、欠载次数/时长、从首次发声到结束与内容时长的差值。固定模拟抖动、持续慢供给、长音频、取消竞态和正式压缩产物都要覆盖。有限缓冲不能弥补持续低于实时的供给速度，也不能把本机合成验收当作真人多浏览器生产验收。最终结果追加于工作项053。
